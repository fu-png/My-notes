## 做了什么修改

### 1. 修复架构缺陷：`hasPptSession` 上下文丢失（`lib/agents/supervisor.ts`）

`isRuleDeterminable()` 判断"规则能否确定意图"时会读取 `context.hasPptSession`（用户是否正处于 PPT 编辑会话），但一旦规则判定"不可确定"、请求转发给 `detectIntentWithLLM()`，这个上下文信号此前完全没有传给 LLM——LLM 的 system prompt 和 user message 都不包含它。这导致用户已经在编辑 PPT 时说出带 PPT 关键词的话，LLM 会无视会话状态、单纯按字面意思判断。

修复方式：在 `detectIntentWithLLM()` 中新增 `sessionNotes`，当 `context.hasPptSession` 为真时，在传给 LLM 的 user message 前面插入一段会话状态说明（"用户当前正处于 PPT 编辑会话中，此时提及 PPT 通常是想修改现有 PPT 而非重新生成"）。验证用例 A57（"帮我把第三页的标题改一下"，`hasPptSession: true`）在修复后 LLM 正确判断为 `chat`。

### 2. 收紧 `isPptIntent` 的排除逻辑，避免复合任务被误伤

原实现中，只要句子任意位置出现"最新/趋势/工具"等词，就整体判定为"查询类语句"从而排除 PPT 意图，导致"搜一下最新更新日志，然后整理成PPT"这种复合任务被误判为纯搜索。

修复方式：把"最新/最近"两个词从强制排除词表中摘出，单独作为 `softQueryIndicators`，只有在句子里**没有**明确的"整理成/做成/生成...PPT"收尾动作时才生效排除；同时新增 `hasExplicitPptOutput` 检测明确的 PPT 产出信号，并加入否定语境识别（避免"不需要生成PPT"被误判为有产出意图）。用一组回归用例验证了原有排除逻辑（A01/A02/A04 等纯提问句）不受影响。

### 3. 补充 supervisor prompt 的边界判断原则（`lib/agents/supervisor.ts` 与 `lib/ai-config.ts` 保持单一来源同步）

在原有"意图类型 + 一句话描述"的基础上，新增四条判断原则：

一是复合任务以最终交付物类型为准，不按句子中任务出现的先后顺序判断，用于修复"搜索+生成PPT"类复合句被误判为纯搜索的问题；二是遇到否定词（不用/不需要/不要/别再）时先排除被否定的意图再判断剩余部分，用于处理"不需要生成PPT，只是想了解原理"这类否定句式；三是提到链接/仓库/视频但当前输入中并无实际 URL 时不要凭空编造，直接判为 chat，用于抑制 LLM 在指代消解失败时的幻觉倾向；四是只要输入包含实际 URL 就一律判为 web_search，不要被"总结/摘要"等词带偏判成 summary，这条是在复测中新发现的问题（见下文）后追加的。

同时把 `translate` 和 `coder` 的描述边界讲清楚："若翻译对象是代码或代码注释，归为 coder 而非 translate"；把 `web_search` 的触发范围收紧为"纯知识性提问、方法论提问不算需要联网，除非明确要求外部最新资料"，避免 LLM 对普通知识性问题也触发搜索。

### 4. 修复过程中额外发现并修正的一个测试标注错误

复测时发现 A58（"再帮我做一份PPT，这次是关于季度总结的"，`hasPptSession: true`）在 `hasPptSession` 修复生效后仍然被 LLM 判为 `ppt`，一开始怀疑是修复没生效，但核实后发现是**测试用例本身标注错误**：这句话包含"再做一份...这次是关于X的"，明确表达了"新主题的新PPT"意图，与 A57 那种单纯编辑现有页面的表达不同，合理的期望结果本来就应该是 `ppt` 而非 `chat`。已将该用例的 `expected` 字段修正为 `ppt`，并在 `note` 中说明这是规则层因 `hasPptSession` 一刀切短路而暴露出的局限——此处恰恰是 LLM 应该纠正规则、识别"新主题"信号的场景。

### 5. 复测中发现的新问题：URL 摘要请求被"总结"关键词带偏

修复 1-3 并跑完整评测后，发现一个新的回归案例 A32（"https://youtu.be/xxx 帮我看看这个视频的内容摘要"），规则版正确判断为 `web_search`，但 LLM 版误判成了 `summary`——单独重复测试三次均稳定复现，说明这不是随机性，而是收紧 `web_search` 描述后，LLM 对"摘要"一词的权重判断超过了对 URL 本身的判断。这正是第 3 项修改里补充的第四条判断原则所修复的问题：明确规定"只要输入中包含实际URL，一律判为 web_search"，修复后重新单独验证三次全部通过。

## 当前仅剩的 1 个失败案例

A44「这玩意儿最近咋样了，有啥新动静没」，期望 `web_search`，规则和 LLM 均判为 `chat`。这句话里"这玩意儿"没有任何明确所指（既无URL也无此前对话上下文可供指代消解），属于单轮意图识别的合理局限——在没有对话历史输入的情况下，模型无法凭空判断"这玩意儿"指向什么，保守回退到 `chat` 是相对安全的选择（错判为 chat 的代价远小于错判为 web_search 后去搜索一个不存在的实体）。评估后认为不值得为了这一个边缘案例继续收紧规则或 prompt，避免引入新的过拟合风险。

## 结论（第一轮：脚本级评测）

三处代码修改（架构缺陷修复 + 规则收紧 + prompt 边界补充）共同将 LLM 版意图识别在高难度对抗性测试集上的准确率从 88.3% 提升到 98.3%，且验证了没有引入可观测的新回归。规则版准确率基本不变符合预期，因为它的设计定位就是覆盖高频无歧义场景、为 LLM 兜底减负，本次修改也没有让规则变得更激进去抢 LLM 的判断空间。

## 第二轮：真实浏览器环境测试，发现级联路径专属问题

第一轮评测的 `run-eval.mts` 直接 `import` 并单独调用 `detectIntent()` 与 `detectIntentWithLLM()`，这两条路径各自独立运行，并不经过真实线上唯一使用的 `detectIntentSmart()` 级联入口（`hooks/use-chat-flow.ts` 里真实调用的就是这个函数）。级联逻辑的核心是 `isRuleDeterminable()`：一旦它认为某句话"规则能确定"，就直接采用规则结果、完全不再调用 LLM。这个门控逻辑本身是否合理，在第一轮评测中是不可见的。

为了验证真实用户实际会体验到的效果，使用 `catdesk browser-action` 在本地运行的应用（`http://localhost:3000/docs/projects/...`）中把 60 个测试用例逐条手动输入聊天框、点击发送，并通过 `catdesk browser-action '{"action":"console"}'` 读取 `detectIntentSmart()` 内部打的 `[intent]` 日志（区分 `rule`/`llm` 两种来源），逐条比对与 `test-cases.json` 中 `expected` 是否一致。

### 真实环境发现的 5 个不一致案例

| 用例 | 输入 | 期望 | 真实结果 | 根因 |
| --- | --- | --- | --- | --- |
| A06 | "https://github.com/... 不用打开链接，凭你了解说说" | chat | web_search | `isRuleDeterminable()` 只要检测到 `^https?://` 就直接短路成规则判断，完全没考虑句子里"不用打开链接"这个否定语境 |
| A07 | "查一下我上次让你总结的那份文档..." | chat(needsRAG) | web_search | "查一下"命中 `searchPrefixes`，直接短路，忽略了"上次"这种明显指向历史对话而非实时联网的信号 |
| A09 | "搜索引擎的工作原理是什么" | chat | web_search | "搜索"只是"搜索引擎"这个复合名词的前两个字，`startsWith("搜索")` 的朴素前缀匹配把话题词误当成搜索指令 |
| A43 | "不用做PPT了，先帮我把大纲写出来就行" | outline | ppt | `isPptIntent()` 中 `hasKeyword && hasAction` 这一支路没有否定保护（否定保护此前只加在了 `hasExplicitPptOutput` 分支上），导致同时命中"ppt"关键词和"做"动作词时直接判真，抢在 LLM 之前短路 |
| A39 | "关于多智能体编排...资料推荐吗" | web_search | chat | 不属于规则层短路问题（未命中 `isRuleDeterminable` 任何条件，确实转发给了 LLM），而是 LLM 自身在这句存在语义模糊性（"要资料推荐"既可读作知识问答也可读作检索请求）的边界句上判断有分歧，多次复测结果不稳定 |

前四例的共同规律：**规则层的短路判断本身没有考虑否定语境、历史指代、复合名词这些语言现象**，而这些正是第一轮 prompt 层修复（否定语境识别、"最新"排除词收紧等）已经教会 LLM 处理的能力——但规则层抢在 LLM 之前短路，使得这些改进对这几个案例完全没有生效机会。这是脚本级评测（分别独立调用两个函数）无法发现、只有真实级联路径才会暴露的架构性问题。

### 本轮修复

1. **`isPptIntent()`**：给 `hasKeyword && hasAction` 分支补上与 `hasExplicitPptOutput` 一致的否定语境保护（`hasNegation && !hasExplicitPptOutput` 时直接返回 `false`），修复 A43。
2. **`isRuleDeterminable()`**：
   - 新增 `hasSearchNegation`（"不用/不要/别...打开/搜索/查/链接/访问"）与 `referencesPriorContext`（"上次/之前/刚才/前面提到"）两个判断，命中时不再对 URL 或搜索前缀做规则短路，转发给 LLM 综合判断，修复 A06、A07。
   - 新增 `isDefinitionQuestionAboutTopic`，识别"搜索引擎/算法/框架 + 是什么/原理/怎么工作"这类释义型问法，避免"搜索"被当成指令前缀误判，修复 A09。
3. **`detectIntent()`**：抽取共用的 `isCasualChitchat()` 判断闲聊问候/感谢/确认/告别，并让规则版 `chat` 兜底分支在命中闲聊模式时显式返回 `needsRAG: false`（此前只返回 `{ type: "chat" }`，`needsRAG` 字段缺失）。这个问题不在最初的 5 个不一致案例里，而是在改造评测脚本、新增"级联版"评测列后才被发现——`isRuleDeterminable()` 会把"好的，谢谢"“明白了”“hey，在吗”这类问候语判定为规则可确定，此前规则版返回的 `{ type: "chat" }` 缺少 `needsRAG` 字段，与期望的 `needsRAG: false` 不匹配，导致级联路径在这三例上产生新的不一致（A24、A26、A51）。

### 评测脚本增强：新增"级联版"评测列

在 `run-eval.mts` 中新增第三条评测路径，直接调用 `detectIntentSmart()`（与线上完全一致的入口），与原有的规则版、纯 LLM 版并列输出，报告中新增"规则层误短路"（级联判错但纯 LLM 判对）与"级联版全部误判"两个专项统计。这样以后规则层新增短路条件时，能第一时间在脚本评测里发现类似问题，而不必依赖真实浏览器测试才能暴露。

### 修复后复测结果

脚本级联版评测（`npx tsx scripts/intent-eval/run-eval.mts`）：

| 检测方式 | 准确率 |
| --- | --- |
| 规则版 detectIntent | 40.0% |
| 纯 LLM 版 detectIntentWithLLM | 96.7%（该次运行，含正常的 LLM 结果波动） |
| **级联版 detectIntentSmart（真实线上路径）** | **98.3%（59/60）** |

随后在真实浏览器环境中对 A06、A07、A09、A39、A43 以及新发现的 A24、A26、A51 共 8 个案例逐一手动复测，通过 `catdesk browser-action` 输入并读取控制台 `[intent]` 日志：A06/A07/A09/A43/A24/A26/A51 共 7 例修复后全部通过；A39 保持不通过，与脚本级联版评测结果一致，确认是独立于本轮规则层修复的 LLM 判断分歧，不属于回归。

级联版最终仅剩 1 个失败案例：A44「这玩意儿最近咋样了，有啥新动静没」，与第一轮报告中记录的结论一致——这是没有对话历史可用于指代消解的单轮识别局限，保守判为 `chat` 相对安全，评估后不值得为此继续收紧规则或 prompt。

## 结论（第二轮：真实环境验证）

规则层短路逻辑（`isRuleDeterminable()`、`isPptIntent()`）此前完全没有否定语境、历史指代、复合名词的识别能力，导致即使 LLM prompt 已经学会正确处理这些情况，用户仍会在真实使用中遇到被规则层抢先、错误路由的问题——这正是脚本级评测（独立调用未经级联门控的函数）无法发现、必须通过真实浏览器端到端测试才能暴露的一类问题。本轮修复针对性地给规则层补上了同等的否定/上下文感知能力，并顺带修复了一个规则闲聊分支缺少 `needsRAG` 字段的细节问题，级联版（即线上真实路径）准确率从真实浏览器测得的 91.7%（55/60）提升到脚本复测的 98.3%（59/60），且新增的级联版评测列会持续防止此类问题再次潜入而不被发现。

## 复现方式

```bash
npx tsx scripts/intent-eval/run-eval.mts
```

可通过环境变量 `INTENT_EVAL_API_KEY` / `INTENT_EVAL_API_BASE` / `INTENT_EVAL_MODEL` 切换测试所用的模型和 API 端点。评测报告现包含规则版、纯 LLM 版、级联版（`detectIntentSmart`，与线上一致）三条路径的对比数据。
